How Shopify is built

Most of the web shops I work on run on Shopify. You can build a good theme without knowing what happens behind it, but the platform’s limits start to make sense once you do. Why can I not set my own headers? Why does an app run on a different server? Why can checkout only be extended, never replaced? It all follows from how the thing is put together.

1. One application, a million shops

Shopify is not software you install. Every store runs on the same platform, and at its centre is one very large Ruby on Rails application. Shopify deliberately did not break it up into hundreds of microservices. Instead it is a modular monolith: one codebase, one deploy, split into components such as orders, inventory and billing, with strict rules about which component may call which. Shopify even built its own tool, Packwerk, to check those boundaries automatically.

The benefit is that a change touching orders and inventory together is one pull request in one codebase, instead of a coordinated release across several services. The cost is that the boundaries only hold if they are enforced, which is why the tooling exists.

The idea: the hard part of a big system is the boundaries, not the number of servers. You can draw those inside one codebase.

2. Pods: splitting the data, not the code

One codebase is fine. One database for every store in the world is not. Shopify solves that with pods. A pod is a self-contained copy of the data layer, with its own MySQL databases, caches and queues. Every store lives in exactly one pod, and the same application code runs against all of them.

  • Scaling means adding pods, not making one database bigger.
  • Failures stay small. If a pod has a bad day, only the stores in that pod notice.
  • Busy stores can move. Shopify can move a store from one pod to another while it keeps selling, so one huge flash sale does not slow down the neighbours.

This is also why everything in Shopify is tied to a single store. A request always belongs to one store, which tells the platform which pod to talk to. Queries across stores are never something you get to do.

3. Reading is a different job from writing

On a storefront, almost every request is a read: show a product, show a collection, show the homepage. Shopify takes those out of the main application and gives them to a separate service, the Storefront Renderer. It reads data, renders Liquid into HTML, caches heavily, and does nothing else.

Writes, such as an order, a stock change or an edit in the admin, go through the core application. In front of all of it sits Cloudflare, which terminates TLS, serves cached responses close to the visitor and absorbs traffic spikes and attacks before they reach Shopify.

The result is that a Black Friday rush on the storefront mostly puts pressure on the part that is built for it, and the admin stays usable for the merchant fulfilling the orders.

4. The theme: Liquid and JSON

A Liquid theme is the part of this most people actually touch. Since Online Store 2.0, a page is no longer one big Liquid file. A template is a JSON file that lists sections, and every section is a Liquid file with a schema describing its settings and blocks:

// templates/product.json
{
  "sections": {
    "main": { "type": "main-product", "blocks": { … } },
    "reviews": { "type": "app-reviews" }
  },
  "order": ["main", "reviews"]
}

When a merchant drags a section around in the theme editor, Shopify rewrites that JSON. The developer owns the sections, the merchant owns the order and the content, and neither has to touch the other’s files.

Two smaller APIs make a Liquid theme feel more like an app:

  • The Ajax Cart API (/cart.js, /cart/add.js) lets the theme change the cart without a page reload.
  • The Section Rendering API returns the HTML of a single section, so after adding something to the cart you can re-render only the cart drawer, using the same Liquid as the full page.

What a theme cannot do is run on the server. There are no custom routes, no response headers and no database. Everything dynamic comes from Shopify’s own data, or from an app.

5. Apps live somewhere else

An app is not a plugin running inside Shopify. It is a separate web application on its own server, talking to the store through the Admin API. The merchant approves a list of scopes when installing it, such as read_orders or write_products, and the app gets an access token limited to exactly those.

  • In the admin, an app usually shows up embedded: Shopify loads it in an iframe and App Bridge connects the two, so it feels like part of the admin.
  • On the storefront and in checkout, apps add things through extensions. Those are small bundles the app uploads to Shopify, which Shopify then hosts and runs. That is how a reviews app gets a block into the product page from the JSON above.
  • Going the other way, Shopify sends webhooks to the app when something happens, such as a new order or a changed product.

The Admin API is GraphQL, and its rate limit is based on query cost instead of request count. Every query has a calculated cost, and each app has a bucket of points that refills over time. Asking for one field is cheap; asking for 250 products with all their variants is not. It pushes you towards asking for exactly what you need.

6. Headless: bring your own front-end

The Storefront API is a public GraphQL API for everything a shopper does: products, collections, cart, customer account. With it you can drop the Liquid theme entirely and build the front-end in anything.

Shopify’s own answer is Hydrogen, a React framework built on React Router, hosted on Oxygen, which runs your code in workers close to the visitor. You get full control over routes, rendering and headers. In return you take on everything the theme layer used to do for you: caching, SEO, the theme editor merchants were used to, and the hosting.

I only reach for headless when the front-end really needs something a theme cannot do. A well-built Liquid theme is fast, cheap to run and editable by the merchant, and that is hard to beat.

7. Checkout: one, owned by Shopify

Every store shares the same checkout, hosted by Shopify. That is not just convenience. It is the part that handles card data, so it is the part Shopify keeps closest. The old checkout.liquid, where you could edit the checkout’s HTML and add your own scripts, has been retired. Today you extend checkout in two ways:

  • Checkout UI extensions add interface: a gift note field, a loyalty banner. They run sandboxed in a web worker and describe their UI with Shopify’s components, so they never touch the real page.
  • Shopify Functions change the logic: discounts, shipping options, payment methods, cart validation. You write them in Rust or JavaScript, they are compiled to WebAssembly, and Shopify runs them inside its own infrastructure under strict time limits.

Functions are the interesting part architecturally. Instead of Shopify calling your server during checkout and waiting for an answer, your code gets shipped to Shopify and runs next to the data. No network round trip, and checkout never depends on your server being up.

8. Custom data without a database

Because you cannot add tables to Shopify, custom data goes into metafields and metaobjects. A metafield adds a typed field to something that exists already, such as a care label on a product. A metaobject is a type of your own, such as “designer” with a name, a photo and a bio, that products can point to. Both are editable in the admin, readable from Liquid and available through both APIs, so the data lives in the same place as everything else and comes along to whichever front-end you use.

9. What this means for security

The architecture draws a clear line. Shopify runs the servers, the network, the TLS certificates, the checkout and the card data. Everything on the edges is yours: the theme code, the apps you install and the access they get, the staff accounts, and any app or headless front-end you build. I wrote about hardening those parts in a separate post on pentesting and hardening.

The idea: Shopify is one monolith split into pods, with a fast lane for reading storefronts and a locked room for checkout. Everything you build plugs in at the edges, and the limits you run into are usually those edges doing their job.
