Porting React components to a site without React

This site is plain HTML, CSS and JavaScript. No build step, no framework, and GSAP from a CDN for the animation. That works well right up until I find a component I like on a site such as 21st.dev or shadcn, because those almost always come as React, styled with Tailwind and animated with framer-motion.

At that point there are two options. Add a toolchain to the whole site for one component, or port the component. I port. The liquid glass carousel under "Recent work" on the homepage and the scrolling hero on every case study page both started as React components. This is how I go about it.

1. Read what it does, not how it is written

The first step is not code. I write down what the component actually does on screen, one behaviour per line. For the case study hero, the original "SmoothScrollHero" came down to four things:

  • an image starts as a window in the middle of the screen and opens up as you scroll
  • the image zooms out slightly while it opens
  • a few smaller images drift past at different speeds
  • the content below rises in as it comes into view

That list is the spec. The hooks, the props and the JSX are just one way of producing it, and most of them have nothing to do with how it looks.

2. Map the hooks onto ScrollTrigger

Framer-motion's scroll animations follow one pattern: read the scroll position with useScroll, map it onto a value with useTransform, and put that value on an element. GSAP's ScrollTrigger does the same thing as a tween with scrub switched on: the scroll position drives the tween's progress directly.

// framer-motion
const { scrollY } = useScroll();
const opacity = useTransform(scrollY, [1500, 2000], [1, 0]);
return <motion.div style={{ opacity }} />;

// GSAP: the same thing, on an element that is already in the HTML
gsap.fromTo('.hero', { autoAlpha: 1 }, {
  autoAlpha: 0,
  ease: 'none',
  scrollTrigger: { start: 1500, end: 2000, scrub: true },
});

The rest of the translations are short:

  • whileInView becomes a ScrollTrigger with a start such as 'top 88%', without scrub, so it plays once when the element comes in.
  • useMotionTemplate, which builds a string like a clip-path out of moving numbers, is not needed. GSAP interpolates the numbers inside a string by itself, as long as both ends have the same shape.
  • useRef becomes querySelector, and useState usually becomes a class on an element that the CSS responds to.

The idea: most scroll animation in React is "this value follows the scroll position", and that is exactly what a scrubbed tween is.

3. One number, and let CSS do the rest

Animating five properties in step from JavaScript gets messy, and it puts layout maths in two places. What I do instead is animate a single custom property from 0 to 1 and let CSS work out everything else from it.

/* the card grows from its resting size to the full screen as --p goes 0 → 1 */
.cs-hero__frame {
  top:    calc(var(--y0) * (1 - var(--p)));
  width:  calc(var(--w0) + (100% - var(--w0)) * var(--p));
  height: calc(var(--h0) + (100% - var(--h0)) * var(--p));
  border-radius: calc(0.24rem * (1 - var(--p)));
}
gsap.fromTo(sticky, { '--p': 0 }, {
  '--p': 1,
  ease: 'none',
  scrollTrigger: { start: 0, end: range, scrub: 0.4 },
});

The resting size lives in the CSS, so a media query can give phones a different card without touching the script. If animation is switched off, --p stays at 0 and the card simply sits there. Nothing breaks.

4. Put the data in the HTML, not in props

A React component gets its content as props. On a static site the HTML is already the content, so I let the component read it from there. The carousel takes its projects from the plain project links in the page: image, title, link. Those links are also what you get if your browser cannot run WebGL, so the fallback and the real thing never disagree, and adding a project means adding one link.

5. Leave things out on purpose

A component built as a demo fills a screen on its own. On a real page it has to share the scroll with everything around it, and that changes what is worth keeping:

  • Smooth-scrolling libraries. The hero component imported Lenis. The rest of this site scrolls natively, and one page that suddenly feels different under the mouse wheel is worse than no smoothing at all, so it went.
  • Scroll hijacking. The original carousel turned the vertical mouse wheel into sideways movement, which traps you in the section. In my version only sideways swipes move the row and the normal wheel keeps scrolling the page.
  • Work nobody sees. The carousel is only built when the section comes into view, using an IntersectionObserver. Visitors who never scroll that far never download the textures.

6. Keep reduced motion in mind

Every port checks prefers-reduced-motion. The page should still make sense with the motion removed: the hero becomes a single screen with the image already open, the gallery images sit still, and content fades in instead of sliding.

The idea: a port is a chance to fit the component to the page it lives on, not just a translation. The parts I leave out matter as much as the parts I rebuild.
