Pentesting and hardening a website

A penetration test is attacking a website on purpose, with permission, to find the holes before someone else does. Hardening is what you do afterwards: closing what you found, plus the things around it that make the next hole harder to use. This is how I go about both.

1. Permission first

Before anything else there is a written agreement. It says which domains and environments are in scope, what is off limits (production payments, other customers’ data, denial of service), when testing happens and who to call if something breaks. Testing a site you do not have permission for is not research. In the Netherlands it is computervredebreuk, and good intentions do not change that.

When possible I test a staging environment that mirrors production, with test accounts for every role: a normal user, an admin, and a second normal user. That second user turns out to be the most useful account of all, as you will see in section 4.

2. Recon: what can anyone see?

Attackers start with what is public, so I do too. A surprising amount of what goes wrong is visible before you send a single unusual request.

# subdomains, from certificate transparency logs
curl -s "https://crt.sh/?q=%25.example.com&output=json" \
  | jq -r '.[].name_value' | sort -u

# files and folders that should not be public
ffuf -u https://example.com/FUZZ -w wordlist.txt -mc 200,403

# TLS versions, ciphers and certificate
testssl.sh example.com

What I am looking for:

  • Forgotten hosts. A staging. or old. subdomain still running last year’s code, often with a test admin account.
  • Files left behind. A readable /.git/ folder, a .env file, backup.zip, or source maps that hand over the original front-end code with comments.
  • The stack. Headers, error pages and file names usually tell you the framework and often its version, which tells you which known vulnerabilities to check.
  • The headers themselves. Missing security headers are not a hole on their own, but they show how much attention security got.

3. Sit in the middle

The main tool for a web pentest is an intercepting proxy, such as Burp Suite or OWASP ZAP. It sits between the browser and the site, so every request can be paused, changed and sent again. It makes one thing very clear: everything the browser does can be skipped. A disabled button, a dropdown with three options, a price in a hidden field, a check in JavaScript. With a proxy, none of it exists. The only checks that count are on the server.

For structure I follow the OWASP Web Security Testing Guide and keep the OWASP Top 10 next to it as a reminder of what goes wrong most often. Automated scanners are useful for the obvious things, but the findings that matter most are almost always found by hand, because they depend on what the application is supposed to do.

4. What I find again and again

Broken access control. Number one on the OWASP list, and number one in my reports. Log in as the first user, open one of your orders, and change the number in the URL. If you can now see the second user’s order, the server checked that you were logged in but not that the order is yours:

// before: any logged-in user can read any order
app.get('/api/orders/:id', requireLogin, async (req, res) => {
  const order = await db.order.findUnique({ where: { id: req.params.id } });
  res.json(order);
});

// after: the order has to belong to whoever is asking
app.get('/api/orders/:id', requireLogin, async (req, res) => {
  const order = await db.order.findFirst({
    where: { id: req.params.id, customerId: req.user.id },
  });
  if (!order) return res.sendStatus(404); // not 403: do not confirm it exists
  res.json(order);
});

The same check is missing surprisingly often on file downloads, invoices and admin endpoints that “are not linked anywhere”.

Cross-site scripting. Somewhere a value from the visitor ends up in the page without being encoded: a search term, a name, a URL parameter. If <img src=x onerror=alert(1)> makes a pop-up appear, any script can run there instead, with access to the page and the user’s session.

No rate limiting. A login form that accepts a thousand passwords a minute, a password reset that sends unlimited emails, a contact form that becomes a spam relay.

Errors that say too much. A stack trace with file paths, a database error with the query in it, or a login that says “unknown email” for one address and “wrong password” for another, which tells anyone which accounts exist.

Outdated dependencies. A package with a known vulnerability and a public exploit is the cheapest attack there is, because someone else already did the work.

Secrets in the wrong place. API keys in a front-end bundle, or in a commit from two years ago that was “removed” in the next one. Git history keeps everything.

5. The report

A finding nobody can reproduce does not get fixed. Every finding in my reports has the same parts: where it is, the exact steps to reproduce it, what an attacker could actually do with it, how serious that is, and a concrete fix. The report starts with a short summary for whoever decides on budget, because “three high findings, one of which exposes customer addresses” gets action faster than forty pages of detail.

After the fixes I test again. A fix that blocks the exact request from the report but not a slightly different one is common enough that a retest is part of the job, not an extra.

6. Hardening: the headers

Headers will not fix a broken access check, but they make many other bugs much harder to use. This is the set I start from:

Strict-Transport-Security: max-age=31536000; includeSubDomains
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-{random}';
  object-src 'none'; base-uri 'none'; frame-ancestors 'none'
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()
  • HSTS makes the browser use HTTPS for a year, even when someone types the address without it.
  • CSP is the important one. With a fresh nonce on every response, only scripts you wrote into the page can run, so an injected script is blocked even if it got through. Roll it out as Content-Security-Policy-Report-Only first and watch what it would have blocked.
  • frame-ancestors 'none' stops other sites from loading yours in an invisible frame to trick clicks.
  • The other three stop browsers guessing file types, keep full URLs out of other sites’ logs, and switch off device features the site does not use.

On a static host that does not let you set headers, a <meta http-equiv="Content-Security-Policy"> tag gets you most of CSP. frame-ancestors and reporting do not work in a meta tag, though, so for those you need a host or CDN that lets you add headers.

7. Hardening: cookies and sessions

Set-Cookie: __Host-session=…; Path=/; Secure; HttpOnly; SameSite=Lax
  • HttpOnly: JavaScript cannot read it, so an XSS bug cannot steal the session.
  • Secure: only sent over HTTPS.
  • SameSite=Lax: not sent along with form posts from other sites, which blocks most cross-site request forgery.
  • The __Host- prefix: the browser only accepts the cookie if it is secure, set for the exact host and for the whole site, so a subdomain cannot overwrite it.

On top of that: issue a new session ID at login, end sessions on the server at logout instead of just deleting the cookie, and offer two-factor authentication, at least for admins.

8. Hardening: input and output

  • Validate on the server, against what is allowed rather than what is forbidden. An amount is a positive number below a limit; a country is one of a known list.
  • Never build a query out of strings. Parameters keep data and code apart: db.query('SELECT * FROM users WHERE email = $1', [email]).
  • Encode output for where it lands. HTML, an attribute, a URL and a script each need different escaping. Use the template engine’s automatic escaping and treat every way of switching it off as something to justify in review.
  • Check permissions on every request, for every object. Not once at login, and not by hiding the button.

9. Hardening: dependencies

Most of the code on a modern site was written by someone else. Commit the lockfile so every install is the same. Let Dependabot or npm audit report known vulnerabilities, and actually merge the updates. Remove packages nothing uses any more. For scripts loaded from a CDN, add a hash so the browser refuses a file that has changed:

<script src="https://cdn.example.com/library@2.1.0/library.min.js"
        integrity="sha384-…"
        crossorigin="anonymous"></script>

That only works with a pinned version. A URL that always points to the latest release can never have a fixed hash, which is a good reason to pin it anyway.

10. Hardening: everything around the code

  • Least privilege everywhere. The database user of the website cannot drop tables. The deploy key can deploy and do nothing else.
  • Secrets live in environment variables or a secret manager, never in the repository, and get rotated when someone leaves or a leak is suspected.
  • Log what matters: logins, failed logins, permission changes, password resets. Without logs you cannot tell afterwards what happened.
  • Backups that have been restored at least once. A backup nobody has tested is a hope, not a backup.
  • A /.well-known/security.txt with a contact address, so someone who finds a problem knows where to report it instead of posting it online.

11. The short version

  • Get written permission and a clear scope before testing anything.
  • Start with what is public: subdomains, leftover files, headers.
  • Assume every check in the browser can be skipped.
  • Test access control with two accounts of the same role.
  • Report so it can be reproduced, and retest after the fix.
  • Harden with headers, strict cookies, server-side validation, pinned dependencies and least privilege.

The idea: a pentest tells you where the holes are today. Hardening makes sure the next bug someone writes does less damage. You need both, and you need to do them again, because the site keeps changing.
